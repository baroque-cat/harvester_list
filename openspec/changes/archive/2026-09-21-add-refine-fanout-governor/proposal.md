# Proposal: add-refine-fanout-governor

## Why

Search-stage work generation is unbounded. When a query's `total_count` exceeds the transport limit, `_handle_first_page_results` computes `partitions = ceil(total / limit)` and materializes that many refined child tasks with no depth counter, no partition cap and no run budget (`stage/definition.py:341-370`); each child re-enters the same path, so refinement recurses. Production incident 2026-09-21 (systemd host, 4 API providers sharing seed `/sk-[a-zA-Z0-9]{32}/`, total≈46M): search queue reached 3 999 992 / 4 000 000 with ~95 tasks processed, peak RSS 6.9 GB + 7.4 GB swap, OOM kill after ~4 minutes, thousands of real task losses via the persistence drain race (`lost task during persistence`). Offline probe 2026-09-21 reproduces the generator side: one `generate_queries('/sk-[a-zA-Z0-9]{32}/', partitions=46007)` call emits **46 656 children in 0.13 s** (×4 providers = 186 624 first-level tasks instantly); recursion multiplies further. Live calibration the same day (api.github.com/search/code, Bearer auth, 2026-09-21) shows why full enumeration is economically impossible and coverage must be traded loudly: sample children totals are `"sk-000"` → 75 136 (would refine again), `"sk-zzz"` → 934 (paginate), `"sk-i00"` → 24 (leaf); covering 46M results through a 1000-per-query API needs ≥46 000 fetches ≈ 85 hours of pure request time per provider at the configured 0.15 req/s — before any dedup value is considered. Historically this explosion was masked by silent truncation: the default 100 000-slot queue quietly dropped the excess on `queue.Full` (warning-only, no counter — `stage/base.py:274,286-288`); the incident config removed that brake by raising the queue to 4M. The governor converts the de-facto historical ceiling into a declared, deterministic, observable policy instead of either silent drops or OOM.

This change is step R1 of the remediation roadmap (`plan.md`): it is the root-cause fix feeding diseases B (RAM materialization/persistence) and C (aggregation drowned by garbage twins), and the safety precondition for R2 disk-queue backpressure (a single search worker producing unbounded children into its own bounded queue would self-deadlock under blocking puts).

## What Changes

- Add an additive `refine_depth: int = 0` field to `SearchTask` (serialization backward-compatible: absent key in old queue JSON deserializes to 0). Children are created with `parent.refine_depth + 1`; roots stay 0.
- At `refine_depth >= max_refine_depth` a task whose total still exceeds the limit does NOT refine again — it falls through to normal pagination (partial coverage, counted and logged loudly).
- Clamp `partitions` passed to `RefineEngine.generate_queries` to `max_partitions_per_refine` (bounds engine-side materialization too: the 46 656-string spike becomes ≤ ~cap×1.35 observed overshoot), and truncate the returned child list deterministically (sorted) to the cap — the engine's language/size paths return `list(set(...))` whose order is not guaranteed across processes, so admission sorts before truncating.
- Introduce a per-run search-task budget `max_search_tasks_per_run`: refined children are admitted in deterministic sorted order until the budget is exhausted; further children are refused with a counted WARNING (never silently). Root tasks from configured conditions are exempt — a provider's configured conditions always run.
- New tri-mode flag `refine_governor.mode: off | shadow | on` (project paradigm): `off` reproduces pre-change behavior byte-equivalently; `shadow` enqueues everything but counts/logs every would-be refusal (measures coverage price before enforcement); `on` enforces. Default: **`on`** — documented paradigm deviation: without a governor the system provably OOM-dies (incident), and the only historical alternative was silent queue-full truncation; `off`/`shadow` remain one config flip away.
- New `RefineGovernorConfig` section (`mode`, `max_refine_depth=2`, `max_partitions_per_refine=128`, `max_search_tasks_per_run=10000`) with loud validation errors (unknown mode / non-positive caps), following the `AggregationConfig` precedent (`config/schemas.py:511-527`, loader `:146-148`, validator `:455-472`).
- New observability surface `PipelineStatus.refine_metrics` (precedent: `aggregation_metrics`, `core/metrics.py:210`): children_generated, children_admitted, refused_depth, refused_budget, truncated_to_cap, parents_at_depth_cap_paginated, budget_remaining, coverage_estimate (per-parent `min(1.0, admitted×limit/total)`, aggregated min/avg).
- Governance is uniform across generator paths: regex-split children, `language:` fan-out (27) and `size:` fan-out (4) all count as children against the same caps — the refine engine itself is NOT modified (minimal blast radius; `REGEX_MAX_QUERIES`/`REGEX_MAX_DEPTH` env seatbelts remain as engine-level defense in depth).
- **Unchanged:** wire queries and fingerprints (governor selects among engine outputs, never rewrites them), baskets/per-provider attribution (children keep parent's provider+patterns), dedup ids, early-stop semantics (observes executed pages per `(provider, query)`), failure-handling contract (children are ordinary tasks under `failure_handling`), aggregation layer (fewer, denser twins raise its TTL hit-rate naturally; locality helpers untouched).

## Capabilities

### New Capabilities
- `refine-fanout-governor`: bounded, deterministic, observable search-work generation — refinement depth cap, per-refine partition clamp, per-run task budget with loud deterministic admission, tri-mode rollout flag, coverage-estimate metrics.

### Modified Capabilities
None. `query-refinement` (clean_regex syntax contract), `search-aggregation`, `search-early-stop`, `failure-handling` requirements are untouched: the governor operates strictly between "engine produced candidate children" and "children enter the search queue", and existing specs constrain neither partition counts nor recursion depth.

## Impact

- **Code:** `core/models.py` (SearchTask field + `_serialize_data`/`_deserialize_data`, ~10 lines), `stage/factory.py` (optional kwarg), `stage/definition.py:333-401` (governor consultation in `_handle_first_page_results`; depth-cap fallthrough to pagination; child creation carries `refine_depth+1`), new `search/refine_governor.py` (governor class: clamp/admit/counters/modes, ~150-200 lines), `manager/pipeline.py` (wiring `_configure_refine_governor` following the `_configure_aggregation` precedent `:190-217`, injected via `StageResources.refine_governor` optional field like gather_skip/early_stop), `config/schemas.py` + `config/loader.py` + `config/validator.py` (config section), `core/metrics.py` + status builder (`refine_metrics`).
- **Behavior:** worst-case search tasks per run drop from unbounded (millions) to ≤ budget + roots + page tasks (~10K at defaults ≈ 18.5 h of fetches at 0.15 req/s — sized to fit a daily cycle); coverage of astronomically broad seeds becomes partial BY DESIGN, loudly counted (`coverage_estimate`) instead of silently dropped by queue overflow or killed by OOM.
- **Risks:** under-sized caps reduce harvest breadth → mitigated by `shadow` mode measurement, configurable caps, and coverage metrics; construction-failure fallback defaults to governed (mode `on`, built-in caps) rather than unbounded, because the ungoverned state is the proven incident; cross-process nondeterminism of engine set-ordering → neutralized by sort-before-admit.
- **Sequencing:** precondition for R2 (`fix-queue-persistence-under-load`: backpressure/blocking puts are safe only with bounded inflow) and force multiplier for R3 (`add-aggregation-locality-v2`: fewer twins, denser FIFO neighborhoods). Composes with landed changes: `fix-silent-losses` (strict retries apply to governed children unchanged), `add-search-aggregation` (cache keys/wire forms untouched), `fix-refine-query-split` (clean_regex contract orthogonal). R0 env seatgaps (`REGEX_MAX_QUERIES`, `REGEX_MAX_DEPTH`) may stay as defense in depth but are superseded as policy by this change.
