# Design: fix-queue-persistence-under-load

## Context

See proposal.md — Why. Current-state facts that shape the approach (all verified by exploration on 2026-09-22):

- Every stage owns a RAM `queue.Queue(maxsize=queue_size)` built in `BasePipelineStage.__init__` (`stage/base.py:155`); sizes come from `config.pipeline.queue_sizes` (`manager/pipeline.py:310,324`; schema defaults search=100 000 / gather=200 000 / check=500 000 / inspect=1 000 000 at `config/schemas.py:120-127`; live `config.yaml` currently 4 M/1.5 M/2 M/3 M).
- The **complete** duck-typed surface used on `stage.queue` across production code: `put(task, timeout=1.0)`, `get(timeout=1.0)`, `get_nowait()`, `put_nowait(task)`, `empty()`, `qsize()`, `task_done()`, raising `queue.Empty`/`queue.Full` (`stage/base.py:229,275,296,306,335-346,354,481,532`; `manager/queue.py:475-487,567`; `manager/pipeline.py:572,596`). `manager/status.py`, `manager/shutdown.py`, `manager/worker.py`, `main.py` never touch `stage.queue` directly — they go through `get_stats()`/`stop()`.
- Persistence: `QueueManager.save_all_queues` → `stage.get_pending_tasks()` (destructive drain + put-back, lossy on `Full` with the incident's signature warning `lost task during persistence`, `stage/base.py:329-350`) → `json.dumps(..., indent=2)` → `AtomicFileWriter.write_atomic` per stage file `{workspace}/queue_state/{stage}_queue.json` (`manager/queue.py:166-214`). Period = `persistence.queue_interval` (60 s; `config/schemas.py:280`).
- **Production durability gap discovered during exploration**: `GracefulShutdown` (`manager/queue.py:494-575`) — the only code doing a final `save_all_queues` — is *never instantiated* in the live path (grep: class def + exports only). Live shutdown is `ShutdownCoordinator` → `TaskManager._on_stop` → `Pipeline._on_stop` (`manager/pipeline.py:356-388`), which calls `queue_manager.stop()` at :385 **without any final save**. So even a clean SIGTERM loses up to `queue_interval` seconds of queued work on the memory backend today.
- Recovery: `TaskManager._on_start` (`manager/task.py:289-329`) unconditionally calls `load_all_queues()` (:298) — note `persistence.auto_restore` is parsed but consumed nowhere — then `_filter_recovery` (:493-512) and `TaskRecoveryManager.recover_queue_tasks` re-`put_task`s everything. `load_queue_state` accepts two envelope formats (new `QueueStateInfo` + legacy fallback) and applies a `max_age_hours=24` gate (`manager/queue.py:216-284`).
- Legacy snapshot wire format — captured sample generated by production `QueueManager.save_queue_state` on 2026-09-22 (probe workspace `/tmp/r2_probe_*`, this repo's HEAD): top-level keys `{stage, provider:"multi", task_count, saved_at:<ISO-8601>, status:"active"|"empty", tasks:[...]}`; each element of `tasks` is exactly `TaskFactory.to_dict()` output, e.g. SearchTask `{"type":"SearchTask","task_id":"<uuid4>","provider":"qwen-maas","created_at":<float>,"attempts":0,"data":{query,regex,page,use_api,address_pattern,endpoint_pattern,model_pattern},"refine_depth":0}` (**top-level** `refine_depth`, pinned by `tests/test_rfg_stage_integration.py:193-203`); AcquisitionTask `data:{url,key_pattern,retries,address_pattern,endpoint_pattern,model_pattern}`; CheckTask/InspectTask `data:{service:{address,endpoint,key,model},custom_url,retries[,source_url_hash]}`. All payloads are JSON-native (no sets/enums inside queue dicts).
- SQLite DNA to mirror (`storage/registry.py`): writer conn `sqlite3.connect(path, check_same_thread=False, timeout=30.0)` + `PRAGMA journal_mode=WAL` + `PRAGMA synchronous=NORMAL` (:462-464); no `busy_timeout` pragma anywhere project-wide; schema bootstrap = idempotent `_DDL` executescript + additive `_migrate_schema` + `PRAGMA user_version = N` (:266-282); readers use URI `?mode=ro` + `timeout=5.0`; degrade-once-per-kind logging (:1063-1067); `start()` never raises (:447-482); stop-drain-commit-close (:484-520). One-shot importer precedent: `tools/registry_migrate.py`.
- Test-surface audit (full report drove D3/D8): the 199-test suite has **zero** coverage of `QueueManager`/`get_pending_tasks`/snapshot formats/`GracefulShutdown`. The only pins constraining this change: `tests/test_fh_stage_modes.py` (dedup gate contract :183-192, worker requeue counters+log text :151-173, `stage.queue.empty()` inside `_wait_drain` :98, stats exposure :272-280) and `tests/test_sa_baskets_e2e.py:143-168` (start → 2×`put_task` → `stop(3.0)` drains bounded, 0 zombies). No test passes `queue_size=` to a stage ctor; all four stage subclasses forward `**kwargs` (`stage/definition.py:74,532,667,870`).
- Environment: Python 3.14.7, sqlite3 lib 3.53.4 (RETURNING supported; WAL default-capable). Single-process, multi-threaded runtime.

## Goals / Non-Goals

**Goals:**
- Make enqueue loss structurally impossible under the `sqlite` backend (no capacity drop, no drain race, no snapshot staleness window).
- Keep the memory backend byte-identical (rollback = config flip; existing pins green unmodified).
- Preserve strict FIFO per stage and the exact dedup/retry/counter semantics on both backends.
- Crash-safe at-least-once resume: SIGKILL/OOM mid-run loses zero acknowledged-enqueue work.
- One-shot, idempotent import of legacy `{stage}_queue.json` snapshots with the existing age gate.
- Close the clean-shutdown final-save gap for both backends.
- Land R3-readiness: rows carry `dedup_id` and monotonic `seq` so a later `ORDER BY fingerprint_group, seq` needs only an additive migration.

**Non-Goals:**
- No lazy child-generation cursor (D9), no hot/cold spill tiering (D2), no cross-process queue sharing, no priority reordering, no compression/backup rotation of the sqlite files, no resurrection or deletion of `GracefulShutdown` (D11), no change to result-shard persistence, registry, or aggregation, no `__slots__`/RSS watchdog (R4), no touching `auto_restore`'s dead-flag status (documented, out of scope).

## Decisions

### D1 — Storage core: per-stage SQLite table with claim/ack lifecycle (the plan.md-recommended mechanism)

New engine `storage/task_queue.py`, class `SqliteTaskQueue`. Schema (`user_version = 1`, additive-only migrations thereafter, mirroring `storage/registry.py:266-282`):

```sql
CREATE TABLE IF NOT EXISTS tasks (
    seq           INTEGER PRIMARY KEY AUTOINCREMENT,  -- strict FIFO order
    dedup_id      TEXT NOT NULL,                      -- stage _generate_id() value (observability/R3; NOT unique — see D4)
    payload_json  TEXT NOT NULL,                      -- ProviderTask.to_dict() verbatim (captured format above)
    attempts      INTEGER NOT NULL DEFAULT 0,         -- task.attempts at insert time (observability)
    state         TEXT NOT NULL DEFAULT 'pending' CHECK (state IN ('pending','claimed')),
    claimed_until REAL,                               -- visibility timeout deadline; NULL while pending
    created_at    REAL NOT NULL                       -- task.created_at (age gate parity)
);
CREATE INDEX IF NOT EXISTS idx_tasks_state_seq ON tasks(state, seq);
CREATE INDEX IF NOT EXISTS idx_tasks_claimed ON tasks(claimed_until) WHERE state='claimed';
```

Lifecycle: `put` = INSERT (committed before returning True). `get(timeout)` = claim oldest pending row (`UPDATE ... SET state='claimed', claimed_until=:now+vt WHERE seq=(SELECT seq FROM tasks WHERE state='pending' ORDER BY seq LIMIT 1) RETURNING payload_json`, single statement ⇒ atomic). `task_done()` = DELETE the calling thread's claimed row (ack). Startup reclaim = `UPDATE tasks SET state='pending', claimed_until=NULL WHERE state='claimed'` (crash orphans) — at-least-once, matching the project doctrine (dedup-ID idempotent downstream, registry upserts idempotent). Expired-claim sweep (`claimed_until < now` → back to pending) runs on the existing `QueueManager` periodic loop for the pathological stuck-worker case.

*Rejected alternative*: NDJSON append-only journal + compaction (plan.md's fallback) — rejected because R3 needs ordered group queries (`ORDER BY fingerprint_group, seq`) and compaction reintroduces an O(N) rewrite; sqlite is already project DNA.

### D2 — Pure-disk single tier: no hot-RAM window under `sqlite`

Every enqueued task lives only in the db file; RAM holds the transient row being handed to a worker. Footprint becomes O(workers), curing disease B1 radically (incident: 4 M × ~0.8–1.2 KB ≈ 3.5–4.5 GB → ~0). Wakeups use a `threading.Condition` broadcast on insert (no polling latency; `get(timeout=1.0)` waits on the CV, claims under the lock, raises `queue.Empty` on expiry — same contract as today).

*Rejected alternative*: hot RAM queue (~10 K) + overflow spill to cold layer (plan.md lists it as complementary). Rejected because two tiers break strict FIFO unless every item carries a global sequence and consumers merge tiers by it — i.e., the hot tier degenerates into a pointer cache over the same seq space, adding a pump thread and dual-state sync bugs for zero durability gain. FIFO adjacency is load-bearing: aggregation TTL-cache hits depend on twins being enqueued consecutively (disease C analysis, plan.md; `order_tasks_for_locality` in `manager/task.py:455`). Throughput headroom makes the hot tier unnecessary: post-R1 the worst observed burst is ~128 children per refine parent and ~10³ links per search hit; single-row WAL commits run at ≥10⁴/s (Group-1 probe will measure the real number before implementation locks in).

### D3 — One db file per stage: `{workspace}/queue_state/{stage}_queue.sqlite`

Mirrors the per-stage `{stage}_queue.json` layout (importer finds legacy files naturally), eliminates cross-stage writer contention (WAL allows one writer per *file*; four stages would otherwise serialize on one file), and bounds corruption blast radius per stage. Connection config copies the registry DNA verbatim: `sqlite3.connect(path, check_same_thread=False, timeout=30.0)`, `PRAGMA journal_mode=WAL`, `PRAGMA synchronous=NORMAL`. All access serializes through one internal `threading.Lock` around the single connection (one-writer discipline, plan.md stone #2); no separate writer thread is needed because inserts are synchronous-by-design (D6 durability contract) and volumes are low (D2).

*Trade-off accepted*: `synchronous=NORMAL` in WAL can lose the last committed transactions on **machine** crash/power loss (not on process kill — the OOM-kill incident class is fully covered since committed rows survive process death in the OS page cache). Consistent with `registry.sqlite`; documented in README.

### D4 — Dedup gate stays in-memory; `dedup_id` column is NOT UNIQUE

The pinned contract (`tests/test_fh_stage_modes.py:183-192`) admits bounded requeues: a retry does `put_task(same task)` **before** the worker's `finally: task_done()` acks the old claim (`stage/base.py:513-532`). A UNIQUE index on `dedup_id` would reject that insert (old claimed row still present) or force ON CONFLICT REPLACE, which deletes the row the pending ack refers to — breaking ack accounting. Therefore: dedup remains exactly today's bounded in-memory set+deque (`stage/base.py:158-161,262-284`), untouched; the column exists for observability and R3 grouping. Post-crash duplicate replay is acceptable (at-least-once doctrine); dedup memory starts empty on every boot today anyway.

### D5 — Claim tracking via thread-local stack; `task_done()` keeps its zero-arg signature

`queue.Queue.task_done()` takes no arguments, and the worker loop (`stage/base.py:532`) relies on that. `SqliteTaskQueue` maintains a `threading.local()` stack: `get()` pushes the claimed `seq`, `task_done()` pops and DELETEs it; an **unpaired call raises `ValueError("task_done() called too many times")`, exactly like stdlib `queue.Queue`** (implementation: `storage/task_queue.py::task_done`). This is reachable only if a caller acks without a preceding successful claim — the production worker loop cannot hit it, because its `finally: self.queue.task_done()` (`stage/base.py:625`) sits inside the block entered after a successful `get()`, while `except queue.Empty: continue` is handled one level out (`stage/base.py:627-629`). Stdlib parity was chosen over silent no-op so that an accounting bug surfaces loudly instead of leaking claimed rows forever. Workers process one task at a time per thread ⇒ depth 1 in practice; the stack is defensive. Crash between claim and ack leaves the row claimed ⇒ reclaimed at startup (D1). *Rejected alternative*: stamping the claim id onto the task object (transient attribute) — mutates shared model instances and leaks storage concerns into `core/models.py`.

### D6 — Enqueue durability contract: `True` means committed; failures are loud, counted, never silent

Under `sqlite`, `put_task` returns True only after the INSERT transaction commits. There is no capacity bound ⇒ `queue.Full` is unreachable ⇒ the drop-on-full branch (`stage/base.py:287-289`) never fires. If a runtime write error occurs anyway (disk full, I/O error), `put` raises the underlying sqlite error, `put_task` catches it, logs WARNING, increments new counter `tasks_dropped_backend_errors` on the stage (exposed via `StageMetrics`, parallel to `tasks_dropped_max_retries` at `core/metrics.py:102`), and returns False — the caller-visible contract (`bool`) is unchanged. Under `memory`, behavior is bit-for-bit today's (1 s bounded put, drop+warn on Full) — the fix for those semantics *is* the backend switch, keeping rollback honest (D8).

*Rejected alternative*: blocking put on the memory backend (plan.md stone: safe only with governor or spill). Not done: it would change rollback semantics, and with R1 governing search inflow the memory backend's bounded drop is tolerable *as the explicitly-legacy option*.

### D7 — Fail-open construction: unopenable store ⇒ memory backend + loud ERROR + degraded marker

If `SqliteTaskQueue` open/bootstrap fails (unreadable dir, corrupt file, permission denied), the stage constructor falls back to `queue.Queue` and logs ERROR naming the stage and cause; the stage records `queue_degraded=True` surfaced in logs/stats. Harvest availability is the primary function; a disk problem must not zero the entire run. This deliberately mirrors the *shape* of R1's D1 fail-safe (construction failure never crashes wiring) while inverting the *direction* (R1 fell back to the restrictive governed state because ungoverned = proven OOM; here the fallback is the permissive memory backend because failing hard = no harvest at all, and memory is today's proven behavior). The degrade is loud, not silent — the house fail-open idiom (`storage/registry.py` degrade-once-per-kind, gather-skip/early-stop kill switches).

### D8 — Config surface: `queue.backend: memory|sqlite`, default `memory`; opt-in promotion

New `TaskQueueConfig` dataclass in `config/schemas.py` (named to avoid collision with the runtime `QueueConfig` in `manager/queue.py`):

```yaml
queue:
  backend: memory          # memory | sqlite
  visibility_timeout_s: 300  # sqlite: reclaim claims older than this (stuck workers)
  max_age_hours: 24          # startup/import age gate (parity with QueueConfig.max_age_hours)
```

Validation (loader + `config/validator.py`): backend ∈ {memory, sqlite}; `visibility_timeout_s > 0`; `max_age_hours > 0` — invalid values fail loudly at load (house pattern: `RefineGovernorConfig`). Wiring: `Pipeline._create_stages` passes `queue_backend=self.config.queue.backend` and `queue_dir=<workspace>/queue_state` into every stage ctor (all subclasses forward `**kwargs` — verified). Under `sqlite`, `pipeline.queue_sizes` entries are ignored (disk is the bound; logged once at startup) — `Pipeline._create_stages` emits a one-time WARNING listing the configured sizes when an operator pairs `backend: sqlite` with non-default `queue_sizes`, so the surprise is visible (`manager/pipeline.py::_create_stages`; `config/validator.py` stays limited to hard errors that funnel into `ValueError("Configuration validation failed")`).

*Deviation from the tri-mode paradigm, justified*: `off|shadow|on` exists for risk *policies* whose divergence is measurable in flight (aggregation, governor). A storage backend is binary infrastructure: shadow double-write would mean running two queues and comparing counts — doubled complexity for a parity claim that tests + the live gate establish better. Rollback story is identical to tri-mode: flip one config key, restart, no code change. Default `memory` follows the aggregation promotion track (ship dark → prove live → flip in `config.yaml`), not R1's default-`on` (which was justified by an active incident *in this subsystem*; the incident-class fix here is durability, and memory remains a supported, bounded-loss option).

### D9 — Scope cuts with rationale (recorded so silence isn't mistaken for oversight)

1. **Lazy child-generation cursor** (plan.md R2 list): superseded by R1's clamp-before-generate (`partitions ≤ 128` ⇒ materialization spike ≤ ~173 strings per parent, measured 144→128 live). A cursor also conflicts with fingerprint-ordered admission, which must see the full candidate list to sort and truncate. Cut.
2. **`fingerprint` column for R3 grouping**: deferred to R3 itself; `ALTER TABLE ADD COLUMN` is the house additive-migration pattern (`storage/registry.py:273-282`) and `dedup_id`+`seq` already give R3 what it needs to prototype `ORDER BY`. Cutting it keeps R2 lean.
3. **`_extract_tasks_from_queue`** (`manager/queue.py:468-491`): unused fallback that duplicates the drain race; left untouched (dead-code removal is cosmetic churn outside this change's risk budget).

### D10 — Shutdown durability for both backends: final save in `Pipeline._on_stop`

Insert `self.queue_manager.save_all_queues(self.stages)` immediately before `self.queue_manager.stop()` in `Pipeline._on_stop` (`manager/pipeline.py:385`), guarded try/except-log so shutdown never hardens. Order rationale: stages are already stopped at that point (workers joined, `accepting=False` since `stop_accepting` ran), so the save observes a quiescent system — no drain race even on memory. Under `sqlite` the call is a cheap no-op-plus-checkpoint (D12). This fixes the discovered production gap (clean SIGTERM losing ≤60 s of queue) independently of backend choice. `GracefulShutdown` stays dead code, untouched (D9.3 spirit).

### D11 — Module placement & facade roles

`SqliteTaskQueue` lives in `storage/task_queue.py` (house: storage engines live in `storage/` — registry, early_stop, gather_skip, key_ledger). `BasePipelineStage` selects the backend in its ctor from injected kwargs. `QueueManager` remains the facade/orchestrator: legacy-format knowledge (importer), periodic sweep+checkpoint scheduling, `get_state_info` reporting. `manager/queue.py`'s JSON paths stay intact for the memory backend.

### D12 — QueueManager under `sqlite`: snapshots become maintenance

`save_all_queues` with sqlite-backed stages performs **no drain and no serialization**: per stage it runs `sweep_expired_claims()` + `PRAGMA wal_checkpoint(PASSIVE)` (bounded file growth) and refreshes state info. `load_all_queues` returns `{}` for sqlite-backed stages after running startup maintenance (reclaim orphans, apply age gate: `DELETE FROM tasks WHERE created_at < now - max_age_hours*3600`, log deleted count loudly) — recovered tasks need no re-`put_task` because they are already in the store the workers claim from; `TaskRecoveryManager.recover_queue_tasks` simply receives nothing for those stages (its per-stage loop skips empties, `manager/recovery.py:48-50`). `get_state_info` reports pending/claimed counts + db file size through the existing `QueueStateMetrics` fields (`state/models.py:233-243`), status ACTIVE/EMPTY by pending count.

### D13 — Legacy importer: one-shot, idempotent, both envelopes, rename-after-success

At startup under `sqlite` (inside `load_all_queues`, before maintenance): for each stage, if `{stage}_queue.json` exists **and** the db has zero rows **and** the snapshot passes the age gate (`saved_at`, both formats parsed exactly as `load_queue_state` does today, `manager/queue.py:236-272`), bulk-insert all deserializable tasks in one transaction (per-task deserialize failures are skipped with a WARNING — parity with today's :244-246), then rename the file to `{stage}_queue.json.imported-<utc-ts>`. Zero-rows guard + rename make re-import impossible (double protection); aged-out snapshots are renamed `.expired-<utc-ts>` without import (loud WARNING, parity with :274-276). Renamed files are kept, not deleted — rollback to `memory` + manual rename restores the old world. Importer precedent: `tools/registry_migrate.py` (idempotent upserts + trust marker).

### D14 — Ordering interplay: startup sequence stays exactly as-is

`TaskManager._on_start` order (pipeline.start → registry run → load_all_queues → filter → recover → periodic save → initial tasks, `manager/task.py:289-329`) is preserved. Under `sqlite`, orphan-reclaim happens earlier — inside queue construction (before any worker starts) — so `load_all_queues` only imports/sweeps/reports. Imported rows get fresh `seq` values ⇒ they precede the run's new inserts ⇒ FIFO puts recovered work first, matching memory-backend recovery semantics (recovered tasks are `put_task`ed before `_create_initial_tasks` today).

## Risks / Trade-offs

- [Per-op SQLite latency on burst enqueue (handler loops `put_task` per link)] → WAL+NORMAL single-row commits measure ≥10⁴/s (Group-1 probe gates this: 10 k sequential puts must complete < 2 s on target hardware); worst realistic burst ~10³ links ≈ tens of ms once per search task vs ~6.7 s per API call at `base_rate 0.15`. If profiling ever shows pain, a batched `put_many` is an additive change.
- [Disk grows where RAM used to] → ~0.3–0.6 KB/row; even the incident-scale 4 M rows ≈ 1.2–2.4 GB of *disk* (vs 3.5–4.5 GB RSS + swap death); WAL checkpointed every `queue_interval`; acked rows DELETEd promptly; optional `VACUUM` documented as ops task, not automated.
- [`empty()`/`qsize()` become COUNT queries polled by `stop()` drain-wait (10 Hz) and status loops] → indexed partial scans over ≤10⁵–10⁶ rows are sub-ms; status cadence is seconds. Acceptable; probe measures.
- [At-least-once replay after crash re-runs in-flight tasks (claimed-but-unacked)] → doctrine-compatible: search/gather/check/inspect side effects are idempotent (dedup-ID gate, registry upserts, shard appends dedupe on recovery reads `storage/persistence.py:_process_shard_generic`). Documented in README.
- [Two connections to one db file (stage writer + a stray reader)] → all reads go through the owning `SqliteTaskQueue` instance's connection under its lock; `QueueManager` asks the instance, never opens the file itself; connect `timeout=30.0` covers checkpoint overlap.
- [Corrupt db file at startup] → open/bootstrap raises ⇒ D7 fail-open to memory + ERROR; operator can delete the file to start clean (documented).
- [Secrets at rest] → CheckTask/InspectTask `service.key` plaintext in `payload_json` — identical exposure to today's queue JSON in the same directory; no regression, noted in proposal Impact.
- [`queue_sizes` silently ignored under sqlite] → one-time startup WARNING listing configured sizes + validator WARNING (D8); metrics still report true pending counts via `qsize()`.
- [Behavioral drift between backends] → parity test matrix (tests.md §P) runs the pinned dedup/retry/drain contracts against **both** backends; fh/sa suites stay green unmodified (regression gate).

## Migration Plan

1. Ship dark: default `backend: memory` — zero behavior change on upgrade; sqlite path exercised by unit/integration tests + parity matrix.
2. Live gate (tasks Group 7, real credentials per operator authorization): incident-seed run on `sqlite` in a temp workspace; SIGTERM restart resumes; **SIGKILL mid-run → restart → claimed rows reclaimed, zero loss, harvest continues**; RSS flat; importer run against a seeded legacy JSON.
3. Promote: flip `config.yaml` `queue.backend: sqlite` (operator step, like aggregation shadow→on); optionally lower `queue_sizes.search` toward ~100 K afterwards (plan.md R0 item — under sqlite the cap is moot, under memory-rollback it re-bounds loss).
4. Rollback: flip back to `memory`; imported `.imported-<ts>` files can be renamed back; sqlite files are inert leftovers.
