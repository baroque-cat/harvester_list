## 1.3 Границы программы (нарушение = остановка и вопрос оператору)

1. **Не трогать `search/github/refine/`** — алгоритм дробления вне маршрута (решение оператора 2026-10-01, plan.md I.15.5; канон §0.1 следствие 3: «расширение покрытия = поворот конфигурационных ручек, не правка движка»). Всё строится ВОКРУГ генератора: слой допуска, SQL, стадии.
2. **Дефолты схемы остаются узкими** (ответов оператора, раунд 2, п.6): 128/10000/24ч и пр. не меняются — wide-профиль живёт только в боевом конфиге прод-хоста. Исключение с явным обоснованием: новый ключ `snapshots_enabled` (дефолт False — производный артефакт без потребителей, пинов нет).
3. **Fail-open доктрина** сохраняется во всех новых слоях (лучше потерять один запрос, чем зависнуть); **единственное исключение — purge-CLI: fail-CLOSED** (разрушающая команда отказывается действовать при неоднозначности). Никаких UNIQUE-ограничений, способных уронить конструктор очереди в memory-backend (H3/R16).
4. **Откат = переворот флага / возврат чисел** (инвариант 4): каждый волновой пакет независимо откатен; новые поведенческие механизмы за трёхпозиционными флагами `off|shadow|on`.
5. **Мёртвая зона (1000, 37000) на API не лечится до web-волны** (ответов оператора, раунд 2, п.5): floor-knob `min_partitions_per_refine` (F7) отложен в волну 6.
6. **Enrichment (`repo_pushed_at`) остаётся выключенным** (понижен оператором: матрица II.21 — врёт до 12.5 лет для вопроса «новая утечка или старая»); даты = `file_commit_date` через file_dating.
7. **R6 (знаменатель partitioning) не воскрешается**; `coverage_estimate` остаётся с маркером `(unfit-denominator)`, при широком клампе документируется как оптимистичная верхняя граница (F10).

## 1.5 Ключевая арифметика горизонта (почему вариант A обязателен)

Совокупная корзина поиска: `github_api` per-credential 0.15 req/s × 4 PAT = **0.6 req/с** (II.23.2). Потолок выдачи GitHub: 1000 результатов на запрос (абсолютный).

| Схема | Запросов на 10⁶ distinct wires | Время при 0.6 req/с |
|---|---|---|
| Вариант B (per-provider перечисление, ×4 избыточность) | 4·10⁶ | **≈77 суток** |
| **Вариант A (fan-out: один fetch на wire)** | 10⁶ | **≈19.3 суток** ✓ горизонт оператора |

Следствие: выбранные «10⁶ за 19 суток» достижимы при текущих 4 токенах **только с вариантом A**; альтернативный рычаг — добавление токенов (исключительное право оператора, канон §0.2). Wall-clock целью не является и не оспаривается; здесь он использован только для выбора архитектуры.

**Единицы горизонта (поправка 2026-10-21, F-11 → OPEN-9):** «10⁶» встречается в трёх несовместимых единицах (distinct wire-fetches / полностью перечисленные wires / страницы). Рабочая трактовка арифметики выше: **10⁶ distinct wire-fetches (page-1 касаний)**; полное перечисление 10⁶ wires со всеми страницами — мультицикловая цель (~10⁷ fetches ≈ 193 суток при 0.6 req/с). Окончательная фиксация единицы — за оператором (OPEN-9); до неё все сайзинги (док 06) даны по режимам, а не по одной цифре.

## 1.6 Термины

| Термин | Значение |
|---|---|
| **wire** | точный запрос на проводе: API — `clean_regex`-литерал в кавычках (`"sk-0d7"`), web — raw дословно (`querykey.py:12`) |
| **wire_fp** | `fingerprint(query, use_api)` = sha256(`"<api\|web>\|<wire>"`) — транспортно-разделённая идентичность (`querykey.py:41-45`) |
| **бакет** | множество совпадений одного wire; `total ∈ (1000, ~37000)` = мёртвая зона API (§1.3.5) |
| **кламп** | `max_partitions_per_refine`; форма ребёнка — функция клампа (канон §0.1: 128→1 литерал/36 wires; 1296→2/1296; 46656→3/46656) |
| **wire-покрытие** | новая SQL-таблица: какой бакет уже перечислен (цель 2a) |
| **fan-out / бенефициар** | одна загрузка владельца раздаётся всем провайдерам-первооткрывателям (образец R17 gather; цель 3b переносит на search) |
| **профиль purge** | разрешённая комбинация обнуления (см. `05_purge_cli.md`) |
| **идентичность Н9.4** | арифметика созданного/поставленного/потерянного, сходящаяся до единицы по опубликованным счётчикам |
