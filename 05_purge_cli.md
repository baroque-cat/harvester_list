## 5.1 Форма команды

`main.py` сегодня — плоский argparse (`main.py:424-460`: `-c/--config`, `--timeout`, `--stats-interval`, `--log-level`, `--validate`, `--create-config`). Добавляется **опциональный subparser** `purge` (dest=command, default None ⇒ все существующие вызовы байт-совместимы):

```
python main.py purge <profile> [-c CONFIG] [--workspace DIR] [--dry-run] [--backup-to DIR] [--yes]
```

- `--dry-run` — первый класс: полный перечислительный проход (области, строки, файлы, байты), ноль изменений, exit 0. Без `--dry-run` требуется `--yes` (защита от случайного запуска в скриптах).
- Воркспейс резолвится из `--workspace` ИЛИ `global.workspace` конфига; **учётки не нужны и не читаются**: purge-ветка не инициализирует провайдеров и не требует credentials-секцию (валидатор в этой ветке пропускает credential-check — явный дизайн-пункт, иначе «обнулить» нельзя без живых токенов).
- Офлайн полностью; работает под 3.11 (AST-пин annotation-hygiene покрывает новый модуль автоматически).

## 5.2 Матрица профилей

Хранилища (верифицировано): реестр — таблицы `links, link_coverage, keys, runs, repos, meta, file_meta, key_sources` (+ `wire_coverage` после волны 3a), **файл `registry.sqlite` ОБЯЗАТЕЛЬНО вместе с `-wal`/`-shm` sidecar (N-10, поправка 2026-10-21: свежая БД рядом с устаревшим WAL — как минимум salt-mismatch reset)**; шарды — `data/providers/<name>/shards/{links,material,invalid}/*.ndjson` + sidecar `.index.json`; снэпшоты — `data/providers/<name>/snapshots/*.json`; очереди — `data/queue_state/*.sqlite{,-wal,-shm}`; телеметрия — `data/registry_decisions.jsonl`, `data/aggregation_decisions.jsonl`, консольные захваты воркспейса.

| Профиль | Удаляет | Эффект для пайплайна | Зависимость |
|---|---|---|---|
| `all` | всё вышеперечисленное в воркспейсе | полный ноль = свежий воркспейс | — |
| `links` | `links`, `link_coverage`, `file_meta`, `repos`, `wire_coverage` | skip/share-слои видят неизвестные ссылки ⇒ re-gather всего (это и есть цель обнуления); даты файлов теряются | — |
| `keys` | `keys`, `key_sources` | check_skip/recheck теряют TTL-историю ⇒ ключи перепроверяются | — |
| `queues` | `data/queue_state/*` | незавершённая работа сброшена; следующий старт восстановит из реестра (после 3a) или шардов (до 3a) | только при остановленном процессе |
| `telemetry` | decision-JSONL, консоли воркспейса, снэпшоты | наблюдаемость обнулена, продукт цел | — |
| `shards` | шарды + sidecars + снэпшоты провайдеров | аудит-лог утрачен; **восстановление возможно только из SQL**; **дополнение 2026-10-21 (F-15):** вместе с шардами умирают check-task/invalid-keys восстановление (остаётся шард-based по D-03.4) и `ShardKeyResolver` в recheck (резолвинг ключ→URL полносканирующий) — до отрастания новых шардов; строка последствия ОБЯЗАНА печататься в квитанцию. **Аудит 3a.4 (2026-10-22):** SQL-recovery acquisition-задач реализован (срез 3a.3, флаг `recovery.source`), check-task восстановление остаётся шард-based по D-03.4 — данная строка последствия и предупреждение при `--force` действуют до расширения волны 4 (`key_sources ⋈ links`) | **ГЕЙТ: разрешён лишь после волны 3a** (recovery primary = реестр); до неё — отказ с указанием причины, обход только `--force` + текст предупреждения в квитанции |

Комбинации вне профилей не собираются (fail-closed, §1.3.3 доков): произвольные наборы областей — не интерфейс.

## 5.3 Интерлоки (fail-CLOSED — единственное исключение из fail-open доктрины)

**Lock-файл ИСПОЛНЕН срез 4.1 (2026-10-23)**: `tools/run_lock.py`, `core/exceptions.py::LockHeldError`, интеграция в `manager/pipeline.py:_on_start/_on_stop` и `main.py` refuse-чек. Пайплайновая половина T14 lands; purge-половина lands в срезе 4.2.

1. **Живой процесс — СИММЕТРИЧНЫЙ lock (F-10, редакция 2026-10-21)**: пайплайн начиная с волны 4 пишет `workspace/.harvester.lock` (pid + boot_ts, атомарно O_EXCL, удаляется при штатном стопе), И **`main.py` при старте ОТКАЗЫВАЕТСЯ запускаться при живом lock** (exit≠0, громко) — без этого половина механизма не работает. **Purge сам БЕРЁТ тот же lock на всё время работы** (O_EXCL от своего имени, освобождает атомарно) — односторонняя схема «purge только читает lock» имеет TOCTOU-окно: стартующий пайплайн ещё не успел написать lock, и purge удаляет файлы под открываемыми дескрипторами (POSIX unlink успешен, sqlite продолжает писать в осиротевший inode, следующее открытие создаёт свежую БД ⇒ тихая бифуркация продуктового хранилища). Взаимное исключение в обе стороны закрывает и третью дыру — гонку `Restart=on-failure` против ручного старта, и variant restore-команды. Проверки purge: lock существует И `os.kill(pid, 0)` жив ⇒ **отказ**; pid мёртв ⇒ громкое INFO «stale lock ignored» + продолжение (`os.kill(pid,0)` на переиспользованном PID консервативно даёт «жив» — fail-closed направление, задокументировано как принятое). Fallback до внедрения lock-файла (и для чужих процессов): свежесть `-wal` файлов очередей/реестра — **порог консервативный ≥120 с и только как fallback** (живой-но-простаивающий пайплайн внутри defer-сна/LLM-вызова может не трогать WAL минуту; волна 0 чек 0.10 измеряет распределение mtime-разрывов на проде).
2. **Отсутствующая область**: громкий skip со счётчиком (не крэш) — идемпотентность повторных запусков.
3. **Неоднозначность** (воркспейс не найден, повреждённый sqlite, неизвестный профиль) — отказ ДО любых удалений, сообщение без содержимого данных.
4. **Порядок внутри `all`**: queues → shards/snapshots → telemetry → registry (последним), чтобы прерванный purge не оставил систему в состоянии «очереди есть, реестра нет» (обратное безопаснее: recovery из реестра невозможна, но шард-fallback жив).

## 5.4 Бэкап и квитанция

- `--backup-to DIR`: реестр — NDJSON-дампы затрагиваемых таблиц (построчно, без pretty-print); шарды/снэпшоты — tar.gz; очереди — побайтовые копии `.sqlite`. Квитанция хранит md5 каждого бэкап-артефакта. **Права (F-29, поправка 2026-10-21): бэкап-артефакты содержат собранные секреты открытым текстом (категория 2), перемещённые ВНЕ воркспейса — целевой каталог создаётся 0700, артефакты 0600 (umask-дисциплина AGENTS §1), режим каталога записывается в квитанцию, README несёт предупреждение.** Восстановление из бэкапа — отдельная команда той же волны (`main.py restore --from DIR`, минимум для реестра; полный restore шардов = распаковка вручную, документируется). **Оговорка restore-тулинга (N-11):** legacy `bulk_insert` пишет строки с `dedup_id=''` — невидимые обоим слоям дедупа; restore обязан либо считать dedup_id, либо опираться на zero-rows guard и startup-reconcile (запинить).
- **Квитанция** `workspace/purge_receipts/receipt_<ts>.json`: `{profile, argv, areas: [{area, rows_deleted, files_deleted, bytes_freed}], backup: {path, md5s}?, config_md5, git_head, started_ts, duration_s}`. **Только счётчики и имена — никогда значения** (категория 2: шарды/реестр содержат собранные секреты; stdout и квитанция маскируются дисциплиной `_redact_line` + структурным пином «в выводе purge нет токенов формы ключа»).
- Дисциплина идентична age-gate (C1): громко, со счётчиком, с аудит-следом — два механизма удаления работы обязаны выглядеть одинаково в логах.

## 5.5 Пины (новый `tests/test_purge_cli.py`)

T1 dry-run no-op по каждому профилю (файлы/строки целы, отчёт полон); T2 apply удаляет ровно целевое множество (матрица профиль × область); T3 backup round-trip (дамп → восстановление → счётчики строк совпадают); T4 отказ при живом lock (fake pid = сам тестовый процесс); T5 stale lock игнорируется громко; T6 wal-freshness отказ; T7 shards-гейт до 3a (отказ + `--force` путь с предупреждением в квитанции); T8 отсутствующая область = skip со счётчиком; T9 квитанция: схема + отсутствие значений секретов (фикстурный воркспейс с фейковым `sk-…` в шарде — пин на НЕпоявление в stdout/receipt); T10 порядок удаления в `all` (spy-лог); T11 restore из бэкапа реестра; T12 purge работает без credentials-секции в конфиге; T13 идемпотентность (повторный запуск = нули, exit 0); **T14 (новое 2026-10-21, F-10): взаимное исключение в ОБЕ стороны — purge отказывает при живом lock пайплайна И startup пайплайна отказывает при живом lock purge (fake-pid фикстуры уже есть в T4/T5)**.

## 5.7 Согласованность трёх хранилищ (почему частичный сброс безопасен)

| Состояние после purge | Поведение пайплайна | Приемлемо? |
|---|---|---|
| `links` сброшен, queues живы | задачи gather исполняются и ПЕРЕзаписывают links (upsert) | да, конвергентно |
| `queues` сброшен, links жив | старт восстановит незавершённое из реестра (3a) / шардов (fallback) | да |
| `keys` сброшен, links жив | check_skip видит неизвестные ключи ⇒ перепроверка (стоимость = бюджет провайдера, намеренно) | да |
| `shards` сброшен (после 3a), реестр жив | восстановление из SQL; аудит-лог утерян (осознанный размен) | да, по явному решению |
| `all` | свежий воркспейс | да |

Запрещённых комбинаций нет — потому что профили определены как связные наборы, а не поблочный доступ (§5.2).
