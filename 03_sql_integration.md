# 03. Совмещение дробителя с SQL (цель 2) + даты в масштабе

**Статус:** проект, ждёт подтверждения двух точек (D-03.4, D-03.9). **Дата:** 2026-10-20.

## 3a. Wire-покрытие в реестре + восстановление из SQL

### D-03.1 Таблица `wire_coverage` (SCHEMA_VERSION 6 → 7, аддитивно)

```sql
CREATE TABLE IF NOT EXISTS wire_coverage(
  wire_fp      TEXT NOT NULL,        -- fingerprint(query, use_api): sha256("<api|web>|<wire>") — транспортно-разделён по построению
  patterns_hash TEXT NOT NULL,       -- идентичность набора паттернов провайдера (смена паттернов ⇒ новое покрытие, зеркало gather-skip)
  total_count  INTEGER,              -- total из ответа GitHub на момент исполнения (знаменатель полноты)
  pages_done   INTEGER DEFAULT 0,    -- сколько страниц бакета фактически исполнено
  pages_needed INTEGER,              -- ceil(min(total, LIMIT)/per_page), LIMIT=1000(api)/100(web)
  results      INTEGER DEFAULT 0,    -- сумма собранных ссылок (наблюдаемость)
  first_ts     REAL, last_ts REAL,
  PRIMARY KEY (wire_fp, patterns_hash)
);
CREATE INDEX IF NOT EXISTS idx_wire_coverage_ts ON wire_coverage(last_ts);
```

Дисциплина дома: upsert `ON CONFLICT DO UPDATE` (как links/keys/key_sources — PK здесь безопасен: писатель один, через writer-очередь реестра, никогда не бросает в конструктор стадии; H3/R16 касается только task_queue). `last_ts` монотонный MAX (образец `_DISCOVER_SQL`). Downgrade-safe: старая сборка игнорирует таблицу (round-trip v7→v6→v7 офлайн, образец R13). Провайдер НЕ входит в ключ — пространство перечисления одно на всех (канон §0.2.2); атрибуция — колонкой `owner_provider` (кто платил корзиной) + существующие `link_coverage`-строки на бенефициаров (fan-out R17 уже пишет их).

### D-03.2 Семантика «покрыто»

Бакет считается покрытым, если `pages_done ≥ pages_needed` И `last_ts` свежее `search.wire_ttl_hours` (новый ключ, дефолт **168** — зеркало `gather_ttl_hours`; drift индекса GitHub ловится TTL: сортировка `sort=indexed&order=desc` выносит свежие файлы на первые страницы, повторное исполнение бакета после TTL их поднимает). Прерванный прогон: `pages_done < pages_needed` ⇒ не покрыт ⇒ следующий прогон доисполняет (страницы — отдельные durable-задачи, очередь их уже переживает; таблица лишь не подавляет недоделанный бакет).

### D-03.3 Точка консультации — между guard'ом и бюджетом

Порядок в `select_children` (или сразу за ним в стадии): governor wire-guard (CPU) → **wire-покрытие (один батч-SELECT на родителя, чанки IN ≤ 1000 — урок C3)** → cap → бюджет. Покрытые дети отклоняются ДО бюджета ⇒ **бюджет тратится только на свежие бакеты** — ключевое свойство возобновляемости (серия прогонов по 200k задач накапливает 10⁶ distinct wires, а не перезапускает пространство). Корень всегда исполняется (его `total_count` — data-driven вход партиционирования; цена 1 запрос). Счётчик `refused_wire_covered` + строка рендера (регистр `_RENDERED_METRIC_SURFACES`). Флаг `search.wire_coverage: off|shadow|on`, дефолт **off**; shadow считает, не подавляя.

### D-03.4 Восстановление из SQL вместо шардов (закрывает C4) — ПОДТВЕРДИТЬ

Primary: при старте `_recover_acquisition_tasks` читает НЕ шарды, а реестр — streaming-выборка `SELECT url FROM links WHERE visit_status IN ('discovered','failed')` чанками по 1000 (курсор, bounded RAM ~МБ), глобальный seen-set по `url_hash`, per-boot cap с маркером продолжения в `meta` (громкий INFO при усечении). Это множество = ровно незаконченная работа (вместо 12 268 READ → 1 014 enqueued у P26 получаем сразу целевой набор). P26-стек фильтров (skip decide → share claim) сохраняется поверх выборки. Fallback: при `registry degraded/unavailable` — прежний шард-путь (чанкованный C3-фиксом), громкий WARNING о переключении. Check-task/invalid-keys восстановление остаётся шард-based (объёмы малы). Шарды становятся чистым аудит-логом ⇒ профиль purge `shards` безопасен (док 05). **Точка подтверждения:** допустимо ли, что при погибшем реестре fallback восстанавливает работу из шардов дольше (полная история под фильтрами)?

### D-03.5 Метрики и непрерывность (урок И7)

`uniq_wires` меняет смысл на «новые wire за прогон» — гейты волны 3a сравнивают **distinct work**, а не счётчики; новая мягкая кросс-идентичность: `admitted + refused_wire_covered == post-guard population`. Форма идентичности Н9.4 эволюционирует: `created_search = claims − share_suppressed − covered_suppressed` (пред-регистрируется в `07_verification.md` ДО гейта — уроки P17-ENTRY/P26-aggregation).

## 3b. Search-side share ledger (вариант A — принят @290@)

### D-03.6 Модуль `manager/search_share.py` — зеркало `gather_share.py` (R17, 40 пинов + живой гейт как шаблон)

Ключ `(wire_fp, page)` — без провайдера (ответ = f(wire, page, transport); паттерны применяются ниже, на gather, где R17 уже шарит). API: `claim/take/abandon/to_stats/close`, `threading.Lock`, cap с fail-open + loud-once, три режима `search.share_fetch: off|shadow|on` (дефолт **off**), run-scoped in-RAM; потеря при рестарте компенсируется частично слоем 3a (завершённые wire persisted), внутрипробежные дубли дёшевы (агрегация + корзина платит повторно — приемлемый fail-open).

### D-03.7 Fan-out обязанностей (образец Ф3/R17, инвариант 1)

Владелец исполняет fetch; каждому бенефициару (включая владельца): его `add_links` (свой шард), `_record_discovered`, early-stop `observe((benef.provider, query))`, gather-skip решение по ЕГО `(provider, patterns_hash)`, его gather-задача со СВОИМИ паттернами, его check-задачи с его regex. Строки реестра (`links`) пишутся один раз; `link_coverage` — на каждого (upsert существует). **Ротация владельца:** назначение owner циклически между первооткрывателями (глобальный счётчик % n_providers), иначе провайдер-1 из порядка конфига оплатит всю корзину поиска — канон §0.2.4 (предел эффективности) требует баланса корзин. `RateLimitDeferral` выходит ДО take (S21-зеркало); неуспех → abandon (бенефициары создают свои задачи позже).

### D-03.8 Композиция с агрегацией — НЕ мешает (ответ на вопрос оператора @285@ п.4)

Леджер работает НАД границей задачи (подавление создания), TTL-кэш агрегации — ПОД ней (шаринг ответа): слои аддитивны, счётчики раздельные (образец композиции gather-skip → share-claim в R17). Агрегация продолжает ловить случайных близнецов в пределах 300 с; леджер устраняет структурных близнецов, разнесённых на часы. Канон §0.2.2 прямо называет оба механизма («search responses via aggregation, gather files via gather.share_fetch») — search-share есть распространение того же принципа за TTL-окно, санкционировано каноном.

### D-03.9 Объём и порядок — ПОДТВЕРДИТЬ

Effort M-L (~280–400 строк продукта по оценке Ф3 + пины; горячий путь `_search_worker`). Предлагаемый порядок внутри 3b: сначала ledger без ротации владельца (простой first-claimant, как R17) → гейт off/shadow/on → затем ротация владельца вторым срезом (баланс корзин измеряем: `token_requests` по провайдерам). Альтернатива «сразу с ротацией» — больше риск, меньше итераций.

## 3c. Даты в масштабе (решение оператора: даты обязательны, @287@ п.2)

### D-03.10 Фоновый батчинг = P21 шаг 2 (не задушить gather)

Проблема измерена заранее: при `scope=gathered` λ ≈ 4 файла/с; инлайн-коалесцинг (шаг 1, shipped) даёт ~2.1 файла/батч и требует ~2 POST/с = весь бюджет `github_graphql` + задержка W на каждом gather-вызове. Решение:

1. Gather-воркер кладёт `(owner, repo, path, sha, url_hash)` в **ограниченное** in-RAM pending-множество (cap ~10 000, при переполнении — громкий счётчик `dating_pending_dropped`, fail-open: дата не важнее файла).
2. Отдельный фоновый поток сбрасывает батчи **20–50** через GraphQL-алиасы (`Commit.history(first:1,path:)`, cost=1/батч замерен R12, `graphql_batch_max=50` безопасен).
3. Доставка результата через существующий URL-keyed канал `record_metadata` (урок D14/F1: `links.path` хранит префикс `blob/<rev>/`), монотонный MAX-merge (D7 R12).
4. Вместо wall-clock бюджета (5.0 с на вызов) — троттлинг по глубине pending-очереди; ограниченный drain в `close()` (вписывается в graceful stop ≤150 с).
5. Fail-open на всех путях: смерть батчера ≠ потеря gather.

Ёмкость: 10⁶–10⁷ файлов горизонта ÷ 50 = 20–200 тыс. POST при ~2/с агрегатно (0.5/s × 4 credentials) = **2.8–28 ч, размазанных по 19 суткам** (<6 % корзины); GraphQL-квота 5000 очков/ч/токен против cost=1/батч — недостижима. Gather не задет: синхронная цена воркера = O(1) вставка в множество.

### D-03.11 Промоушен file_dating

После гейта 3c: `file_dating.enabled: true`, `transport: graphql`, `scope: gathered` (боевой конфиг прод-хоста; дефолты схемы узкие — §1.3.2). Enrichment (`repo_pushed_at`) остаётся выключенным (§1.3.6). Fill-rate `file_commit_date` — главная наблюдаемая величина (сейчас 0.0000 во всех живых прогонах).

## 3d. Миграции, пины, откат

- SCHEMA_VERSION 6→7 одной аддитивной миграцией (wire_coverage + meta-маркеры); round-trip v7→v6→v7 офлайн-доказательство (worktree без дефисов, AGENTS §4).
- Пины: contract-пины таблицы (upsert идемпотентен, TTL-истечение, смена patterns_hash ⇒ re-execute, pages_done накопление), чанк-граница IN ≤1000, ledger-пины зеркалят R17 (L/S/C/R-серии), батчер-пины (pending cap, drain, MAX-merge, fail-open), render-пины новых строк.
- Новые способности спек при отгрузке: `wire-coverage`, `search-share` (§1.4); правка `refine-fanout-governor` (бюджет-сценарий) едет с волной 5.
- Откат каждого среза: флаг off (поведение байт-в-байт прежнее) → revert коммита.
