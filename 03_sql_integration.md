## 3a. Wire-покрытие в реестре + восстановление из SQL

### D-03.1 Таблица `wire_coverage` (SCHEMA_VERSION 6 → 7, аддитивно) — ИСПОЛНЕН срез 3a.1 (suite 842→852, 2026-10-22)

```sql
CREATE TABLE IF NOT EXISTS wire_coverage(
  wire_fp      TEXT NOT NULL,        -- fingerprint(query, use_api): sha256("<api|web>|<wire>") — транспортно-разделён по построению
  patterns_hash TEXT NOT NULL,       -- идентичность набора паттернов провайдера (смена паттернов ⇒ новое покрытие, зеркало gather-skip)
  total_count  INTEGER,              -- total из ответа GitHub на момент исполнения (знаменатель полноты)
  pages_bitmap INTEGER DEFAULT 0,    -- битовая карта исполненных страниц (страница N ⇒ бит N-1; ≤10 бит API / ≤5 web)
  pages_done   INTEGER DEFAULT 0,    -- CONTIGUITY WATERMARK: наибольшие N такие, что страницы 1..N все завершены (производное от bitmap, никогда не «+1» и не «MAX(page)»)
  pages_needed INTEGER,              -- ceil(min(total, LIMIT)/per_page), LIMIT=1000(api)/100(web)
  results      INTEGER DEFAULT 0,    -- сумма собранных ссылок (наблюдаемость)
  first_ts     REAL, last_ts REAL,
  PRIMARY KEY (wire_fp, patterns_hash)
);
CREATE INDEX IF NOT EXISTS idx_wire_coverage_ts ON wire_coverage(last_ts);
```

Дисциплина дома: upsert `ON CONFLICT DO UPDATE` (как links/keys/key_sources — PK здесь безопасен: писатель один, через writer-очередь реестра, никогда не бросает в конструктор стадии; H3/R16 касается только task_queue). `last_ts` монотонный MAX (образец `_DISCOVER_SQL`); `pages_bitmap` — монотонный побитовый OR (`pages_bitmap | excluded.pages_bitmap`), watermark пересчитывается из bitmap при каждом upsertе. Downgrade-safe: старая сборка игнорирует таблицу (round-trip v7→v6→v7 офлайн, образец R13). Провайдер НЕ входит в ключ — пространство перечисления одно на всех (канон §0.2.2); атрибуция — колонкой `owner_provider` (кто платил корзиной) + существующие `link_coverage`-строки на бенефициаров (fan-out R17 уже пишет их).

**Gap-safety (F-01, блокер аудита 2026-10-21):** страницы — отдельные durable-задачи; они завершаются ВНЕ порядка, умирают после исчерпания ретраев и дублируются после visibility-redelivery. Наивный `pages_done = pages_done + 1` или `MAX(page)` помечает бакет с дырами (страница 5 готова, 2–4 потеряны) как покрытый ⇒ подавление НАВСЕГДА — ровно класс потерь, который Н9.4 существует ловить. Поэтому: только bitmap+watermark. Обязательные пины: (i) out-of-order (5 раньше 2–4) оставляет watermark=1; (ii) дубль страницы 3 дважды не двигает watermark; (iii) kill-drill с дырой НЕ подавляет бакет в следующем прогоне.

### D-03.2 Семантика «покрыто» — ИСПОЛНЕН срез 3a.2 (suite 852→866, 2026-10-22)

Бакет считается покрытым, если `pages_done ≥ pages_needed` И `last_ts` свежее `search.wire_ttl_hours`. **Сайзинг TTL (F-06, поправка 2026-10-21):** дефолт **168** (зеркало `gather_ttl_hours`) корректен только для УЗКОГО профиля; при широком клампе цикл серии ≈ 19.3 суток > 168 ч ⇒ головные wire истекают СРЕДИ цикла и недельный resweep вечно конкурирует с хвостовой новизной за корзину — утверждение «серия накапливает, а не перезапускает пространство» становится ложным. Wide-профиль: `wire_ttl_hours ≥ длины цикла` (**720**, совпадает с queue age-gate) ИЛИ явный resweep-режим как осознанная политика. Развилка — OPEN-10 (обе стороны config-only). Drift индекса GitHub ловится TTL в обоих профилях: сортировка `sort=indexed&order=desc` выносит свежие файлы на первые страницы, повторное исполнение бакета после TTL их поднимает. Прерванный прогон: `pages_done < pages_needed` ⇒ не покрыт ⇒ следующий прогон доисполняет (страницы — отдельные durable-задачи, очередь их уже переживает; таблица лишь не подавляет недоделанный бакет).

### D-03.3 Точка консультации — между guard'ом и бюджетом — ИСПОЛНЕН срез 3a.2 (suite 852→866, 2026-10-22)

**Точка консультации ЗАФИКСИРОВАНА (F-05, поправка 2026-10-21): IN-GOVERNOR, не «сразу за ним в стадии».** Вариант «за `select_children` в стадии» = ПОСЛЕ бюджета (guard→cap→budget все внутри метода) ⇒ покрытые дети ели бы бюджет, и ключевое свойство «бюджет только на свежие бакеты» (возобновляемость серии) умирает. Механика: trailing-kwarg конструктора `coverage_probe: Optional[Callable[[List[str], bool], Set[str]]] = None` (прецедент `drop_wire_indistinguishable`; запиненные позиционные сигнатуры `test_rfg_governor.py:10-11` целы); порядок внутри `select_children`: **guard → coverage → cap → бюджет**; covered-дети не потребляют ни cap, ни бюджет (зеркало S22-учёта wire-collapse); fail-open — при None/исключении probe ноль подавлений. Стадия передаёт колбэк, делающий ОДИН батч-SELECT на родителя чанками IN ≤ 900–1000 (урок C3; storage остаётся вне `search/`). Корень всегда исполняется (его `total_count` — data-driven вход партиционирования; цена 1 запрос). Счётчик `refused_wire_covered` + токен в КОНЦЕ строки Refine (регистр `_RENDERED_METRIC_SURFACES`). Флаг `search.wire_coverage: off|shadow|on`, дефолт **off**; shadow считает `would_refuse_covered`, не подавляя.

### D-03.4 Восстановление из SQL вместо шардов (закрывает C4) — ИСПОЛНЕН срез 3a.3 (suite 870→890, 2026-10-22)

Primary: при старте `_recover_acquisition_tasks` читает НЕ шарды, а реестр — streaming-выборка `SELECT url FROM links WHERE visit_status IN ('discovered','failed') ORDER BY last_seen_ts DESC` чанками по 1000 (курсор, bounded RAM ~МБ), глобальный seen-set по `url_hash`, per-boot cap с маркером продолжения в `meta` (громкий INFO при усечении; следующий старт продолжает с маркера). **Поправки 2026-10-21 (F-14):** (а) миграция v7 добавляет `idx_links_visit_status ON links(visit_status, last_seen_ts DESC)` — без него полный скан на 10⁷–10⁸ строк каждый старт; (б) `ORDER BY last_seen_ts DESC` ОБЯЗАТЕЛЕН — без порядка cap оставляет СТАРЕЙШИЕ, жертвуя самыми свежими утечками (собственная философия поиска — `sort=indexed&order=desc`); (в) continuation-marker в `meta` делает усечение возобновляемым между стартами. **Ред. 2026-10-22 (D2/D3):** составной курсор `"{last_ts}|{last_url_hash}"` в `meta` (ключ `recovery_cursor:{provider}`) — zero-loss при равных ts на границе усечения (D2 fix); per-provider фильтрация `AND provider = ?` в reader + per-provider meta-ключ — атрибуция legacy-шард-пути, исключение загрязнения маркера между провайдерами (D3 fix). Reader принимает `before_hash: Optional[str]` и применяет ТО ЖЕ keyset-условие `(last_seen_ts < ? OR (last_seen_ts = ? AND url_hash > ?))`, что и within-boot. Legacy ts-only маркер поддерживается с WARNING. Это множество = ровно незаконченная работа (вместо 12 268 READ → 1 014 enqueued у P26 получаем сразу целевой набор). P26-стек фильтров (skip decide → share claim) сохраняется поверх выборки.

**Флаг источника (F-17, поправка 2026-10-21; ред. 2026-10-22, Д14):** `recovery.source: shards|registry|auto`, дефолт **shards** до прохождения гейта 3a, затем **auto** (registry-primary, fail-CLOSED при недоступном реестре — crash с nonzero exit, БЕЗ шард-fallback). Единственный механизм 3a, у которого не было документированного отката, — теперь три-позиционный, как все (инвариант 4).

Check-task/invalid-keys восстановление остаётся шард-based (объёмы малы) — **но см. F-15:** профиль purge `shards` убивает этот carve-out И `ShardKeyResolver` в recheck; поэтому либо 3a расширяется на SQL-восстановление check-задач (`key_sources.url_hash ⋈ links.url` — схема и вид `key_sources_dated` уже соединяют их), либо последствие явно записывается в матрицу дока 05 и квитанцию purge (выбрано второе + предупреждение в receipt; расширение — кандидат волны 4). Шарды становятся чистым аудит-логом ⇒ профиль purge `shards` безопасен ПОСЛЕ закрытия F-15-оговорки (док 05). **OPEN-5 РЕШЁН 2026-10-22 (Д14):** при погибшем реестре программа крашится (fail-CLOSED, nonzero exit), шард-fallback ЗАПРЕЩЁН.

### D-03.5 Метрики и непрерывность (урок И7)

`uniq_wires` меняет смысл на «новые wire за прогон» — гейты волны 3a сравнивают **distinct work**, а не счётчики.

**Форма идентичности (F-02, БЛОКЕР аудита — исправлено 2026-10-21).** Первоначальная запись `created_search = claims − share_suppr − covered_suppr` НЕБАЛАНСИРУЕМА по построению: консультация покрытия стоит ДО claim (D-03.3), поэтому covered-дети до claim не доходят — вычитание `covered_suppr` из `claims` двойной счёт ⇒ отрицательный баланс на здоровом прогоне ⇒ FAIL или импровизация в день гейта (ровно урок точки агрегации P26). Правильная пред-регистрация — **ДВЕ дизъюнктные идентичности + одна кросс-связка**:

1. **Admission (губернатор):** `generated = admitted + refused_wire_collapse + refused_wire_covered + truncated_to_cap + refused_budget` (расширение дизъюнктных сумм S22/S30 — правка пинов пред-регистрируется в 07 §7.9).
2. **Creation (стадия):** `created_search = search_claims − search_share_suppr` (covered-подавленные дети здесь не появляются вовсе — они отброшены на шаге 1).
3. **Кросс-связка очередей:** `rows_end = rows_start + created − processed − aged_out − purge_deleted`, где `aged_out` публикуется из существующего WARNING-счётчика age-purge (при широком режиме ненулевой — член обязателен), плюс отдельный баланс 3c: `dated + dropped = pending_in`.

Все три пред-регистрируются в `07_verification.md` §7.3 ДО гейта (уроки P17-ENTRY/P26-aggregation/F-02).

### D-03.7 Fan-out обязанностей (образец Ф3/R17, инвариант 1)

**Множество бенефициаров (F-07, поправка 2026-10-21):** бенефициары = **ВСЕ включённые провайдеры, разделяющие claim-нувший `patterns_hash`** (fan-out цикл итерирует реестр провайдеров как `recovery.py:175-180`), а не только фактические claim-нувшие. Причина: глубже L1 подавленный близнец ничего не создаёт ⇒ `take()` возвращал бы ОДНОГО владельца ⇒ его шард/coverage/check-задачи копились бы одному провайдеру, а `link_coverage(B, patterns_hash)` осталась бы пустой для миллионов ссылок ⇒ gather-skip для B видел бы coverage_gap и переоткрывал их в следующих прогонах — цель 2 нарушена МЕЖДУ прогонами (контраст с R17: там все бенефициары независимо обнаруживают тот же URL, здесь — нет). Пин гейта 3b: coverage skew ≤1.1× после fan-out (07 §7.4).

Владелец исполняет fetch; каждому бенефициару (включая владельца): его `add_links` (свой шард), `_record_discovered`, early-stop `observe((benef.provider, query))`, gather-skip решение по ЕГО `(provider, patterns_hash)`, его gather-задача со СВОИМИ паттернами, его check-задачи с его regex. Строки реестра (`links`) пишутся один раз; `link_coverage` — на каждого (upsert существует).

**Ротация владельца — механизм ВЫБРАН (F-03, поправка 2026-10-21; прежняя формулировка «глобальный счётчик % n_providers среди первооткрывателей» механически невозможна):** claims происходят в момент создания, подавленный близнец не заявляет ничего, поэтому назначенный счётчиком «владелец» не имел бы задачи в полёте ⇒ wire не fetchится НИКЕМ (потеря, цель 4). Принят вариант **(a)**: **first-claimant owns** (чистое зеркало R17), а баланс корзин достигается ротацией **ПОРЯДКА КОРНЕЙ** между прогонами (per-run seed порядка посевных задач) + атрибуцией `owner_provider` в wire_coverage; гейт измеряет КОМБИНАЦИЮ (`token_requests` по провайдерам ±10 %, 07 §7.4). Альтернатива (b) «генератор создаёт задачу с provider=rotated_owner» отклонена как ломающая атрибуцию поддеревьев. **Композиция с F2 (F-18):** admission-бюджет губернатора платит ДОПУСКАЮЩИЙ провайдер (чей родитель породил wire), корзину search — ИСПОЛНЯЮЩАЯ учётка владельца; ±10%-ожидания обоих гейтов пересчитаны по этому разделению и запинены одним тестом композиции.

**Abandon-семантика (NEW-3/N-09, поправка 2026-10-21):** `RateLimitDeferral` выходит ДО take (S21-зеркало, никогда не abandon); неуспех → abandon. НО проглоченные швы (shadow-swallow `base.py:692-699` и catch-all `definition.py:257-259` — последний закрывается NEW-2 в волне 1) завершают задачу БЕЗ исключения ⇒ без дополнения бенефициары остались бы подавленными на весь прогон молча. Правило: **abandon-in-finally по признаку «StageOutput не произведён»** (владелица-задача завершилась без результата любого вида), никогда на DEFER-пути.

### D-03.8 Композиция с агрегацией — НЕ мешает (ответ на вопрос оператора ответов оператора, раунд 1, п.4)

Леджер работает НАД границей задачи (подавление создания), TTL-кэш агрегации — ПОД ней (шаринг ответа): слои аддитивны, счётчики раздельные (образец композиции gather-skip → share-claim в R17). Агрегация продолжает ловить случайных близнецов в пределах 300 с; леджер устраняет структурных близнецов, разнесённых на часы. Канон §0.2.2 прямо называет оба механизма («search responses via aggregation, gather files via gather.share_fetch») — search-share есть распространение того же принципа за TTL-окно, санкционировано каноном.

### D-03.9 Объём и порядок — ПОДТВЕРДИТЬ

Effort M-L (~280–400 строк продукта по оценке Ф3 + пины; горячий путь `_search_worker`). Порядок внутри 3b (согласован с F-03(a)): срез 3b.1 — ledger first-claimant + fan-out всем same-patterns провайдерам + abandon-in-finally → гейт off/shadow/on; срез 3b.2 — ротация ПОРЯДКА КОРНЕЙ + `owner_provider`-атрибуция + пин композиции F-18 (баланс корзин измеряем: `token_requests` по провайдерам ±10 %, HTTP-правда через `Aggregation misses` — F-27). ## 3c. Даты в масштабе (решение оператора: даты обязательны, ответов оператора, раунд 2, п.2)

### D-03.10 Фоновый батчинг = P21 шаг 2 (не задушить gather)

Проблема измерена заранее: при `scope=gathered` λ ≈ 4 файла/с; инлайн-коалесцинг (шаг 1, shipped) даёт ~2.1 файла/батч и требует ~2 POST/с = весь бюджет `github_graphql` + задержка W на каждом gather-вызове. Решение:

1. Gather-воркер кладёт `(owner, repo, path, sha, url_hash)` в **ограниченное** in-RAM pending-множество (cap ~10 000, при переполнении — громкий счётчик `dating_pending_dropped`, fail-open: дата не важнее файла).
2. Отдельный фоновый поток сбрасывает батчи **20–50** через GraphQL-алиасы (`Commit.history(first:1,path:)`, cost=1/батч замерен R12, `graphql_batch_max=50` безопасен).
3. Доставка результата через существующий URL-keyed канал `record_metadata` (урок D14/F1: `links.path` хранит префикс `blob/<rev>/`), монотонный MAX-merge (D7 R12).
4. Вместо wall-clock бюджета (5.0 с на вызов) — троттлинг по глубине pending-очереди; ограниченный drain в `close()` (вписывается в graceful stop ≤150 с).
5. Fail-open на всех путях: смерть батчера ≠ потеря gather.

Ёмкость: 10⁶–10⁷ файлов горизонта ÷ 50 = 20–200 тыс. POST при ~2/с агрегатно (0.5/s × 4 credentials) = **2.8–28 ч, размазанных по 19 суткам**; уточнение 2026-10-21: «<6 % корзины» держится только на краю 10⁷ (при 10⁶ — 0.6 %). Pending-flush: λ ≈ 4 файла/с заполняет 50-батч за ~12.5 с ≈ 0.08 POST/с ≪ ёмкости 2/с — конкуренции с gather нет. GraphQL-квота 5000 очков/ч/токен против cost=1/батч — недостижима. Gather не задет: синхронная цена воркера = O(1) вставка в множество.
